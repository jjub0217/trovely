# 데모 링크에서 검색과 AI에게 물어보기 열기 설계

- 작성일: 2026-11-25 (수)
- 상태: 사용자 승인 대기
- 관련: `2026-11-24-instagram-import-and-semantic-search-design.md`(RAG 기능 본 설계, PR #7)

## 1. 왜 하나

Trovely RAG 작업의 목적은 이력서에 쓸 경험이다. 채용 담당자와 면접관이 이 경험을 직접 눌러 보고 확인할 수 있어야 한다.
그런데 지금 RAG 기능(비슷한 콘텐츠 검색, AI에게 물어보기)은 로그인한 관리자 계정에서만 동작한다. 운영 사이트는 가입해야 하고, 새 계정에는 저장한 게시물이 없어서 검색해도 보여 줄 것이 없다.
로그인 없이 누구나 들어오는 데모 링크에서 이 기능을 써 볼 수 있게 한다.

## 2. 목표, 하지 않을 것, 실패로 볼 것

목표
1. 데모 링크 방문자 누구나 "비슷한 콘텐츠 더 보기"와 "AI에게 물어보기"를 실제로 쓸 수 있다(미리 저장한 답이 아니라 실제 AI 호출).
2. 하루 사용량에 상한을 둬서, 누가 얼마나 눌러도 하루 요금이 정해진 선을 넘지 않는다.
3. 데모 예시 게시물을 늘려서 "글자는 다르지만 뜻이 비슷한 게시물"을 찾는 장면이 나오게 한다.

하지 않을 것
- 운영 사이트에서 가입자 모두에게 이 기능을 여는 것(개인정보 안내가 먼저 필요하다. 과정은 대화에 정리해 두었고 이번 범위 밖).
- 데모에서 게시물 저장, 수정, 인스타그램 가져오기(지금처럼 막아 둔다).
- 사람마다 다른 상한(로그인이 없어 사람을 구분하지 않는다. 데모 전체 합계로만 센다).

실패로 볼 것
- 데모가 운영 DB에 연결되거나 운영 데이터를 읽고 쓴다.
- 상한을 넘었는데도 AI 요청이 나간다.
- 상한을 넘었을 때 화면이 멈추거나 오류만 보인다(키워드 검색은 계속 돼야 한다).
- 예시 게시물 글이 실제 인스타그램 캡션을 옮겨 온 것이다.

## 3. 사용자가 정한 것

1. 데모는 방문자 모두에게 연다(실제 AI 호출). 대신 하루 횟수를 제한한다.
2. 횟수는 데모 전용 Supabase 프로젝트에 센다(운영 DB와 완전히 분리).
3. 운영 사이트는 가입자 모두에게 열지 않는다. 이 결정에 따라 운영에서는 숫자 목록(벡터) 만들기도 관리자 게시물에만 한다(다른 가입자의 메모와 후기를 구글로 보내지 않기 위해).
4. 사용자는 취업할 때까지 Trovely를 직접 쓰지 않는다(사용자 요청 수는 적다고 본다).

## 4. 설계

### 4-1. 하루 사용량 세기
- 데모 전용 Supabase 프로젝트에 표 하나를 둔다: 날짜, 기능 종류, 횟수.
- AI를 부르기 직전에 "오늘 이 기능의 횟수를 1 올리되, 상한보다 작을 때만" 한 번의 SQL로 처리한다. 두 요청이 동시에 와도 숫자가 틀리지 않는다.
- 상한을 넘으면 AI를 부르지 않는다.
- 날짜는 한국 시각 기준으로 바뀐다.
- 사용량 DB에 연결하지 못하면 AI를 부르지 않는다(세지 못하면 막는 쪽이 안전하다).

하루 상한(데모 전체 합계)과 하루 최대 요금(추정)

| 기능 | 하루 상한 | 한 번에 드는 요청 | 한 번 요금(추정) | 하루 최대(추정) |
|---|---|---|---|---|
| 비슷한 콘텐츠 검색 | 300회 | 검색어 숫자 바꾸기 1번(약 20토큰) | 거의 0 | 약 $0.001 |
| AI에게 물어보기 | AI 요청 60회(질문 약 30개) | 질문 하나 = 질문 읽기 + 답 쓰기 2번(입력 약 3,500토큰, 출력 약 1,000토큰) | 질문 하나에 약 $0.006 | 약 $0.2 |

- 가격 근거: Gemini 공식 가격표(2026-11-25 확인). gemini-3.8-flash 100만 토큰당 입력 $0.75, 출력 $3.75(2026-12-31까지, 2027-01-01부터 두 배). gemini-embedding-001 100만 토큰당 입력 $0.15.
- 토큰 수는 측정하지 않은 추정이다. 출력에는 AI가 생각하는 데 쓰는 토큰이 포함되는데 그 양을 재지 않았다. 그래서 하루 최대는 넉넉히 하루 $1, 한 달 $30 안쪽으로 본다(2027년 가격 기준 두 배).
- 상한 숫자는 설정값으로 둬서 바꾸기 쉽게 한다.

### 4-2. 데모 예시 게시물
- 지금 12개(개발, 요리, 여행, 운동, 인테리어)를 30개 안팎으로 늘린다.
- 비슷한 주제를 묶는다: 사우나(찜질, 노천탕, 해수), 고기집(고깃집, 야키니쿠), 파주 데이트(카페, 레스토랑, 소품샵) 등.
- 일부는 같은 뜻을 다른 낱말로 쓴다(예: 검색어 "고깃집", 캡션 "고기집").
- 일부는 방문 완료 표시를 켠다("안 가 본 곳만"이 실제로 거르는지 보이게).
- 캡션은 새로 지어 쓴다. 실제 가게 이름, 계정 이름, 실제 캡션은 쓰지 않는다.

### 4-3. 예시 게시물의 숫자 목록(벡터)
- 데모에는 DB가 없다. 예시 게시물의 숫자 목록은 실제 Gemini로 한 번 만들어 파일로 저장하고, 데모는 그 파일을 읽는다.
- 예시 게시물 글이 바뀌면 다시 만들어야 하므로, 글이 파일과 맞는지 검사하는 테스트를 둔다.

### 4-4. 데모 화면
- 검색: 엔터를 누르면 키워드 결과(지금 데모와 같음) 아래에 "비슷한 콘텐츠 더 보기"가 나온다. 검색어는 누를 때 실제로 숫자로 바꾸고(상한에서 1 차감), 예시 게시물 숫자 목록과 가까운 순으로 고른다.
- AI에게 물어보기: 데모에서도 봇 버튼을 보인다. 동작은 본 기능과 같다(질문 읽기, 방문 여부 거르기, 5개 건네기, 근거 검사). AI를 부르는 요청마다 상한에서 1 차감한다(질문 하나 = 2, 조건을 ×로 빼고 다시 물으면 1). 질문 하나를 1로만 세면 두 번째 요청만 직접 반복해 보내 상한을 피할 수 있어서다(2026-11-26 구현 중 판단).
- 상한을 넘으면 안내: "오늘 데모에서 쓸 수 있는 횟수를 다 썼어요. 내일 다시 써 주세요." 키워드 검색은 계속 된다.
- 데모 AI 창의 예시 질문은 예시 게시물에 맞춘다(예: "이번 주말 파주에서 안 가 본 데이트 장소 있어?").

### 4-5. 운영 쪽 조정(결정 3)
- 운영에서 숫자 목록 만들기를 관리자 게시물에만 한다. 저장, 수정 뒤 숫자 목록 만들기와 기존 게시물 채우기 스크립트 모두 같다.
- 관리자가 아닌 가입자는 지금처럼 키워드 검색만 쓴다.

## 5. 제약
- 데모 배포에는 운영 DB 주소를 절대 넣지 않는다. 데모가 쓰는 DB는 사용량 표뿐이다.
- 비밀값(사용량 DB 주소, Gemini 키)은 Vercel 데모 프로젝트 환경변수에만 둔다. 화면과 로그에 출력하지 않는다.
- 로컬 개발과 테스트는 로컬 DB에 같은 사용량 표를 만들어서 한다.
- 커밋은 이 브랜치(`feat/demo-rag`, PR #7 브랜치에서 갈라짐)에만. 머지는 사용자가 한다.

## 6. 구현자에게 맡기는 것
- 사용량 표의 정확한 이름과 칸, SQL 모양.
- 데모에서 가까운 순으로 고르는 계산(예시 게시물이 수십 개라 메모리에서 계산해도 된다).
- 예시 게시물의 구체적인 글(4-2 규칙 안에서).

## 7. 내가 정한 것(사용자 확인 전)
- 하루 상한: 검색 300회, AI에게 물어보기 AI 요청 60회(질문 약 30개).
- 사용량 DB에 연결하지 못하면 AI를 부르지 않는다.
- 날짜 기준은 한국 시각.
- 예시 게시물 30개 안팎.
