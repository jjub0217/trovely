# 인스타그램 저장 게시물 가져오기 + 뜻으로 찾기(RAG 검색 단계) 설계

- 작성일: 2026-11-24 (화)
- 상태: 설계 완성, 사용자 최종 확인 대기(구현 전)
- 관련: `2026-03-12-reelbox-design.md`(서비스 처음 설계), `2026-05-24-thumbnail-resilience-design.md`(썸네일 복구)

## 1. 왜 하나

Trovely는 "인스타그램에 저장한 게시물을 다시 찾기 어렵다"는 사용자의 불편에서 시작했다. 그런데 지금 인스타그램에 저장만 하고 Trovely로 옮기지 못한 게시물이 2,831개 쌓여 있다(2021-01 ~ 2026-11). 사용자가 실제로 찾는 방식은 정확한 이름이 아니라 기억나는 조각이다.

- "데이트로 저장한, 사우나"
- "데이트로 저장한, 파주 지역의 사우나"
- "데이트로 저장한, 파주 지역의 맛집"

지금은 "데이트" 컬렉션 113개를 스크롤로 끝까지 훑어야 하고, 훑다가 놓칠까 불안하다.

두 번째 목적은 사용자가 RAG(검색 증강 생성)의 검색 단계, 즉 벡터 검색(뜻이 비슷한 글을 찾는 검색)을 직접 만들어 보고 측정해서 기술 블로그로 남기는 것이다. 블로그 초안: `~/Desktop/blog-drafts/blog-draft-trovely-rag.md`(이 저장소 밖).

## 2. 목표, 하지 않을 것, 실패로 볼 것

목표
1. 인스타그램 "내 정보 내보내기" 파일(JSON)로 저장 게시물 2,831개를 Trovely로 한꺼번에 가져온다. 캡션도 함께 저장한다.
2. 사용자가 인스타그램에서 이미 만든 컬렉션을 카테고리로 살리고, 정리가 덜 된 부분만 AI가 분류를 제안한다. 사용자는 묶음별로 검토한 뒤 저장한다.
3. 기억나는 조각으로 검색하면 맞을 만한 게시물이 위에 오게 한다(뜻으로 찾기).
4. 단어 검색과 뜻 검색을 같은 시험 질문으로 재서 비교한다.

하지 않을 것(이번 범위 밖)
- 찾은 게시물을 AI에게 넘겨 문장으로 답하게 하는 단계(RAG의 생성 단계). 검색 단계 측정 결과를 보고 다음에 정한다.
- 영상 속 말(음성 받아쓰기)과 화면 속 글자(문자 인식) 읽기.
- 커뮤니티 스킬, 로그인 쿠키, 비공식 API로 인스타그램을 직접 긁어 오기(약관과 보안 위험).
- 인스타그램과 계속 동기화. 가져오기는 내보내기 파일을 올릴 때마다 한 번씩 한다.
- 유튜브 게시물 가져오기(내보내기 파일은 인스타그램만).

실패로 볼 것(돌아가더라도)
- 이미 Trovely에 있던 게시물의 카테고리, 태그, 메모, 후기를 덮어쓰거나 중복으로 만든다.
- 사용자가 검토하지 않은 AI 분류가 그대로 저장된다.
- 로컬 작업이나 마이그레이션이 운영 DB를 건드린다(이 저장소 CLAUDE.md의 dev/prod 분리 규칙).
- 뜻 검색이 단어 검색보다 낫지 않은데도 붙여 둔다. 재 보고 아니면 붙이지 않는 것도 정상 결론이다(예전 캐싱 결정과 같은 태도).

## 3. 입력 데이터 (실제 파일로 확인한 사실)

사용자가 받은 내보내기 파일 두 개. 기기로 내보내기, 일부 정보(저장됨), 기간 전체, JSON, 저화질.

`saved_posts.json`
- 배열 2,831개. 각 항목: `timestamp`(저장 시각, 초), `label_values`(라벨과 값 목록).
- 라벨: `URL`(2,831), `캡션`, `제목`, 그리고 라벨 없이 `title`이 붙은 묶음(`해시태그`, `소유자`, `브랜드 파트너`).
- 주소 종류: `/reel/` 2,261개, `/p/` 570개. 주소 중복 없음.
- 캡션이 빈 것 16개. 캡션 길이 중앙값 350자(하위 25% 165자, 상위 10% 936자). 캡션 앞에 붙는 군더더기 없음(microlink 응답과 다름).
- 한 항목에 캡션이 둘 이상인 것 145개(여러 장짜리 게시물로 추정). 첫 번째 것을 쓰거나 이어 붙인다(구현자 판단).
- `media`는 모두 비어 있음. 썸네일 이미지는 파일에 없다.

`saved_collections.json`
- 컬렉션 61개. 각 컬렉션: 이름, 유형, 공개 범위, 업데이트 시간, 그리고 속한 게시물 목록(게시물마다 URL, 캡션 등).
- 컬렉션에 들어간 게시물 2,799개(중복 제거). 컬렉션 밖 32개. 컬렉션 게시물은 모두 `saved_posts`에 있음.
- 게시물 수: 인테리어 833, 해외 여행지 370, 요리 238, 국내 여행지 219, 청소 215, 취준 165, 데이트 113, 위시리스트 50, 사진꿀팁 37, 언젠가 꼭 할 일 24, 패션 21, 영화 20, 개발 17, 운동 15, 계곡 14, 육아 10. 그 밖 42개 컬렉션은 10개 미만(피부 관리 쪽이 많음: 모공, 블랙헤드, 잡티, 선크림 등). 빈 컬렉션 3개(속건조, 경혈아로마오일, 네일).
- 한 게시물이 여러 컬렉션에 있을 수 있다.

글자 깨짐: 문자열이 UTF-8 바이트를 한 글자씩 적은 형태다. 읽을 때 `s.encode("latin-1").decode("utf-8")`로 되돌려야 한글이 보인다. 라벨 이름(`캡션`, `제목`, `이름`)도 같은 방식으로 되돌려 비교한다.

개인정보: 파일에는 다른 사람의 계정 이름(소유자)도 들어 있다. 파일은 저장소에 넣지 않는다(`.gitignore`). 시험이나 개발용 사본은 저장소 밖에 둔다.

## 4. 사용자가 정한 것

1. 가져오기는 공식 "내 정보 내보내기" 파일로 한다.
2. 검토 화면은 "AI가 나눈 묶음별로" 방식(시안 C). "카페 32개"처럼 제안 카테고리별로 묶어 보여 주고, 묶음을 열어 틀린 것만 빼거나 고친 뒤 묶음째 저장한다. AI가 확신하지 못한 것은 "분류 애매" 묶음.
3. AI 분류는 저장하기 직전에 사용자가 고친다(검토 없이 저장하지 않는다).
4. 맞는 카테고리가 없으면 AI가 새 카테고리를 만들어 제안한다. 새로 만든 것은 검토 화면에서 표시한다.
5. 인스타그램 컬렉션 중 큰 것은 카테고리로 그대로 옮기고, 잘게 나뉜 작은 컬렉션, 빈 컬렉션, 컬렉션 밖 게시물은 AI에게 맡긴다.
6. 검색 성공 기준: 정답 게시물이 상위 5개 안에 나오면 성공(맨 위 하나를 맞히는 것이 목표가 아님).
7. 가져오기는 사용자 본인만 쓰는 기능으로 만든다. 기존 관리자 권한(`AdminRole`)이 있는 계정만 가져오기 화면에 들어갈 수 있다. 가입자 전체에게 여는 것은 측정 결과를 본 뒤 따로 정한다. 그래서 다른 사람 파일 대응, 사용자별 AI 호출 한도, 개인정보 안내는 이번 범위 밖이다.
8. 캡션과 메모를 Gemini로 보내는 것은 본인 데이터라 사용자가 정한다. 무료 요금제는 보낸 내용을 구글이 서비스 개선에 쓸 수 있다는 점을 사용자에게 알렸다.
9. (2026-11-24 저녁 바뀜) 무료 등급 Gemini 글 생성이 계속 "수요 많음"(503)과 3분 대기로 실패해서, AI는 카테고리가 필요한 게시물(102개)에만 쓰기로 했다(사용자 결정). 큰 컬렉션 게시물은 AI 제안 없이 바로 검토 목록에 나오고 태그 없이 저장한다. 태그는 나중에 따로 붙인다(이번 범위 밖). 뜻 검색은 캡션을 쓰므로 영향이 작다. 아래는 바뀌기 전 내용: 큰 컬렉션 게시물(약 2,700개)의 AI 태그는 묶음째 저장하면 검토한 것으로 본다. 사용자는 묶음을 열어 훑고 이상한 것만 고친 뒤 저장하고, 태그는 저장 뒤에도 수정 화면에서 고칠 수 있다. 위 "검토하지 않은 AI 분류가 그대로 저장"되는 실패 기준은 카테고리 제안(작은 컬렉션, 컬렉션 밖 게시물)에 적용하고, 태그는 이 규칙을 따른다.

## 5. 설계

### 5-1. 데이터 모델 변경

- `Reel`에 캡션 저장 칸을 더한다(예: `caption String?`). 가져온 게시물과, 앞으로 새로 저장하는 게시물 모두에 쓴다.
- 해시태그는 캡션 안에도 있으므로 따로 저장하지 않아도 된다(구현자 판단).
- 저장 시각: 내보내기의 `timestamp`를 `createdAt`으로 쓸지는 구현자 판단. 목록 정렬이 최신 저장 순이므로, 인스타그램에서 저장한 시각을 살리는 쪽이 사용자 기대에 가깝다(내 판단).
- 벡터 저장: Supabase의 pgvector 확장을 켜고, 게시물마다 벡터 하나를 저장하는 칸이나 표를 둔다. Prisma는 vector 타입을 직접 다루지 못하므로 `Unsupported("vector(N)")`와 raw SQL을 쓴다. 로컬 Docker Supabase에도 같은 확장이 켜져야 한다.
- 가져오기 검토 대기 상태: 사용자가 저장을 누르기 전의 AI 제안을 어딘가 보관해야 한다. 임시 표(가져오기 작업과 제안 목록)를 두는 방식이 자연스럽다. 저장이 끝나면 지워도 된다.

### 5-2. 가져오기 흐름

1. 사용자가 `saved_posts.json`과 `saved_collections.json`을 올린다(로그인한 본인만).
2. 서버가 글자 깨짐을 되돌리고, 게시물별로 URL, 캡션, 저장 시각, 속한 컬렉션 이름들을 만든다.
3. 이미 Trovely에 같은 URL이 있는 게시물은 건너뛴다(`@@unique([url, userId])`). 기존 게시물의 카테고리, 태그, 메모, 후기는 건드리지 않는다. 캡션 칸이 비어 있다면 캡션만 채우는 것은 허용(구현자 판단).
4. 분류 규칙
   - 게시물 10개 이상인 컬렉션(16개)은 같은 이름의 카테고리로 옮긴다. 이미 같은 이름의 카테고리가 있으면 그것을 쓴다. 이 게시물들은 AI 분류 없이 "확인만" 하는 묶음으로 보여 준다.
   - 10개 미만 컬렉션의 게시물과 컬렉션 밖 게시물은 AI가 캡션을 보고 카테고리를 제안한다. 기존 카테고리(위 16개 포함) 중에서 고르고, 맞는 게 없으면 새 이름을 제안한다. 작은 컬렉션끼리 큰 카테고리로 합치는 것이 기대하는 동작이다(예: 모공, 블랙헤드, 선크림 → 피부 관리).
   - 10이라는 기준은 내 판단이다. 설정값으로 두어 바꾸기 쉽게 한다.
   - 빈 컬렉션은 옮기지 않는다.
   - 한 게시물이 여러 컬렉션에 있으면 해당 카테고리를 모두 붙인다.
5. 태그: AI가 캡션과 해시태그를 보고 게시물마다 몇 개(3~5개 안팎) 제안한다. 태그는 검토 화면에서 고칠 수 있고, 저장 뒤에도 기존 수정 화면에서 고칠 수 있다.
6. 검토 화면(시안 C): 제안 카테고리별 묶음 목록 → 묶음 열기 → 게시물별로 빼기, 카테고리와 태그 고치기 → 묶음째 저장. "분류 애매", "새 카테고리" 표시, 진행 정도(전체 몇 개 중 몇 개 저장) 표시.
7. 저장하면 `Reel`, 카테고리, 태그 연결을 만들고 벡터를 만든다.

AI 호출 양: AI 분류는 작은 컬렉션과 컬렉션 밖 게시물(대략 100개 안팎)만, 태그 제안과 벡터 만들기는 2,831개 전부다. 한 번에 여러 게시물을 묶어 보내고, 요청 한도에 걸리면 기다렸다 이어서 하도록 만든다. 가져오기가 한 번의 요청 시간(Vercel 함수 시간 제한) 안에 끝나지 않을 수 있으므로, 나눠서 진행하고 이어 할 수 있어야 한다.

### 5-3. 썸네일

내보내기 파일에는 썸네일이 없다. 2,831개를 가져오는 순간 모두 받으면 microlink 요청 한도(이 컴퓨터에서 확인한 값은 하루 5건 수준, 추정)에 바로 걸린다. 그래서 가져올 때는 썸네일을 비워 두고, 화면에 카드가 보일 때 기존 복구 장치(`refreshThumbnail`)로 그때그때 받는다. 지금 `ReelThumbnail`은 `src`가 처음부터 비어 있으면 복구를 시도하지 않으므로, 비어 있는 경우에도 한 번 받아 오도록 고친다. 썸네일을 못 받은 카드는 지금처럼 대체 화면을 보여 준다. 요청 한도를 피하는 다른 방법(Iframely 키, 받기 순서 조절)은 구현자 판단.

### 5-4. 뜻으로 찾기

- 벡터로 바꿀 글: 캡션 + 카테고리 이름 + 태그 + 메모 + 후기를 이어 붙인 글. 게시물 내용이 바뀌면(수정, 태그 변경) 벡터도 다시 만든다.
- 벡터를 만드는 API: Gemini의 텍스트 임베딩 모델을 쓴다(사용자가 이미 Gemini를 써 봤고 한국어를 지원). 모델 이름과 차원 수는 구현자가 공식 문서로 확인해 정한다. API 키는 다른 비밀값처럼 로컬 `.env.local`과 Vercel 환경변수에 두고 화면에 출력하지 않는다.
- 검색: 카테고리 필터(기존 기능)로 먼저 좁히고, 그 안에서 검색어 벡터와 가까운 순으로 정렬한다. "데이트로 저장한"은 뜻 검색이 아니라 카테고리 필터로 처리하는 것이 정확하다. 화면은 기존 검색창을 쓰고, 단어 검색과 뜻 검색을 바꿔 볼 수 있게 한다(측정과 블로그용). 기본값을 무엇으로 둘지는 측정 결과를 보고 정한다.
- 개인정보와 비용: 캡션과 메모가 Gemini API로 전송된다. 게시물 2,831개 수준이라 비용은 작을 것으로 보이나, 구현자가 현재 가격과 무료 사용량을 확인해 계획에 적는다.

### 5-5. 측정

- 시험 질문 10개 안팎. 사용자의 세 문장과 같은 모양("카테고리 + 지역 + 종류")으로 만들고, 각 질문의 정답 게시물을 미리 정한다. 정답이 실제로 데이터에 있는 질문만 쓴다. 질문 초안은 구현자가 만들고 사용자가 "내가 실제로 이렇게 찾을 것 같다"인지 확인한다.
- 비교 대상: 단어 검색(지금의 `contains` 검색에 캡션을 더한 것)과 뜻 검색. 공정하게 같은 카테고리 필터를 건다.
- 주 기준: 정답이 상위 5개 안에 든 비율. 보조 기준: 상위 5개에 섞인 엉뚱한 게시물 수.
- 이미 본 단어 검색의 약점(기대 가설): "스파"가 "스파이시", "인스파이어"에 걸림. "고기"가 지명 "고기리"에 걸림. "찜질 코스", "해수 찜질"처럼 '사우나'라는 말이 없는 사우나 게시물을 놓침.
- 결과는 블로그 초안 작업 로그와 본문에 남긴다.

## 6. 제약

- 이 저장소 CLAUDE.md 규칙: 로컬은 Docker Supabase, `.env`에 로컬 DB 주소, 운영 비밀값은 Vercel에만, 운영 마이그레이션은 Session pooler(5432)로 따로, DB 페이지는 `force-dynamic`.
- 커밋, 푸시, 머지는 사용자가 요청할 때만. 작업은 최신 main에서 새 브랜치로(지금 체크아웃은 `feat/demo-mode`).
- 데모 모드(`DEMO_MODE`)에서는 가져오기와 AI 호출이 동작하지 않거나 막혀야 한다.
- 개발 순서는 단계별로 끊고 단계마다 확인한다: 가져오기와 캡션 저장 → 분류 제안과 검토 화면 → 썸네일 → 벡터와 뜻 검색 → 측정.
- 로컬에서 먼저 만들고 측정한다(로컬 Docker DB에 사용자 파일로 가져오기). 운영 DB 반영(pgvector 확장 켜기, 마이그레이션, 실제 가져오기)은 측정 뒤 사용자 확인을 받고 한다(내 판단).

## 7. 구현자에게 맡기는 것

- 임시 표 구조, 서버 액션과 API 경로 나누기, 배치 크기, 재시도 방식.
- AI 분류와 태그 제안에 쓸 Gemini 모델과 프롬프트(확신도 기준으로 "분류 애매"를 가르는 방법 포함).
- 임베딩 모델과 차원, pgvector 색인 종류.
- 검토 화면의 세부 모양(시안 C의 틀 안에서).
- 캡션이 여러 개인 게시물 처리, 캡션 빈 16개 처리.

## 8. 내가 정한 것(사용자 확인 전)

- 작은 컬렉션 기준 10개(16개 옮김, 42개 AI).
- 큰 컬렉션 게시물은 AI 분류 없이 "확인만" 하는 묶음으로 보여 주고, 태그는 2,831개 전부 AI가 제안.
- 인스타그램 저장 시각을 `createdAt`으로 쓰는 쪽을 권장.
- 썸네일은 화면에 보일 때 받아 오기.
- 임베딩은 Gemini.
- 검색은 카테고리 필터 + 뜻 정렬, 단어/뜻 전환 가능.

- (점검 후 내가 정한 것) 카테고리는 사용자가 기존 카테고리 필터(칩)로 고른다. 검색어 문장에서 카테고리 이름을 자동으로 뽑아내지 않는다. 시험 질문도 "카테고리 선택 + 나머지 검색어"(예: 데이트 선택 + "파주 사우나")로 나눠 두 검색에 똑같이 넣는다. 지금 단어 검색은 띄어쓰기로 나눈 낱말을 모두 만족해야 하므로(AND), 비교할 때 이 동작을 그대로 쓴다고 기록한다.
- (점검 후 내가 정한 것) 뜻 검색 모드에서는 고른 카테고리 안에서 가까운 순으로 상위 20개를 보여 주고, 비슷한 정도로 잘라 내지 않는다. 기존 정렬 메뉴와 이어 불러오기는 뜻 검색 모드에서 끈다. 화면에 "뜻으로 찾은 결과(가까운 순)"라고 표시해 일반 목록과 구분한다.
