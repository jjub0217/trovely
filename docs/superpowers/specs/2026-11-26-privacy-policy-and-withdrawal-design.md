# 개인정보 처리방침과 회원탈퇴 정리 설계

- 작성일: 2026-11-26 (목)
- 상태: 사용자 기준 합의(2026-11-26), 구현 완료, 운영 값 확인 대기
- 브랜치: `feat/privacy-withdrawal` (main에서 갈라짐)

## 1. 왜 하나
- 운영 사이트에 개인정보 처리방침이 없다. 이메일을 받는 서비스라 공개해야 한다.
- 회원탈퇴를 해도 Supabase 로그인 계정(이메일, 카카오 회원번호, 닉네임)이 남고, 탈퇴 기록에 이메일과 직접 쓴 사유가 기한 없이 남았다. 이대로는 처리방침에 "탈퇴하면 삭제"라고 쓸 수 없다.

## 2. 사용자가 정한 기준
1. 탈퇴 기록에는 탈퇴 날짜와 선택형 사유만 남긴다. 이메일, 사용자 ID, 소셜 식별 정보, 직접 쓴 사유는 남기지 않는다. 이미 남은 정보도 정리하되, 삭제 전에 대상과 영향을 먼저 확인한다.
2. 보호책임자는 실명, 문의 메일은 Trovely 전용 계정(사용자가 만들어 알려 줌).
3. 탈퇴 때 Supabase 계정까지 삭제, 구글과 카카오 연결 해제 필요성 확인, 재가입과 예전 세션 차단 검증, 일부 실패 시 탈퇴 완료로 처리하지 않기, 관리자 가입자 수는 활성 계정 기준.
4. 처리방침은 로그인 없이 보이게, 출시하지 않은 AI 기능은 쓰지 않고 지금 실제로 처리하는 정보 기준, 외부 서비스의 위탁과 국외 이전 확인, 실제 보유와 삭제 방식과 일치.

## 3. 구현
- 탈퇴: 앱 데이터 삭제, 탈퇴 통계 기록, Supabase 계정 삭제를 한 DB 트랜잭션에서 처리. 계정 삭제가 실패하면 예외로 전부 되돌리고 화면에 오류를 보여 준다.
- 탈퇴 창의 직접 입력 칸을 없앴다(원문을 받지 않으면 보관할 일도 없다).
- 카카오: 사용자 토큰을 저장하지 않으므로 앱 어드민 키(`KAKAO_ADMIN_KEY`)와 카카오 회원번호로 연결을 끊는다. 계정 삭제 뒤에 시도하고, 실패해도 탈퇴는 완료로 본다(내 판단: Trovely 데이터는 이미 없고 카카오 쪽 연결 목록에만 남기 때문).
- 구글: Supabase 로그인만 쓰고 구글 토큰을 저장하지 않는다. Trovely가 끊을 수단이 없고, 이용자가 구글 계정 설정에서 끊을 수 있다고 처리방침에 적는다.
- 미들웨어: 쿠키만 읽던 `getSession()`을 서버에 확인하는 `getUser()`로 바꿨다. 지워진 계정의 예전 쿠키로 접속하면 `/` ↔ `/login` 무한 이동이 생기는 것을 로컬에서 재현하고 고쳤다. 대신 페이지 요청마다 Supabase 인증 서버 확인이 한 번 늘어난다.
- 관리자: 가입자 수 = auth.users 수. 회원 목록의 "탈퇴" 필터와 탈퇴 상세 창, 탈퇴 목록의 이메일과 상세 사유 칸을 없앴다.
- 처리방침: `/privacy`(로그인 없이), 가입, 로그인 화면 아래와 사이드바에 링크. 운영 값은 `src/lib/privacy-info.ts`에 모으고 "[확인 필요]"가 남아 있으면 배포하지 않는다.

## 4. 운영 반영 순서
1. 운영 Supabase SQL Editor에서 `scripts/privacy-cleanup/1-check.sql` 실행 → 숫자 확인
2. 진행하기로 하면 `2-delete-withdrawn-accounts.sql` 실행(되돌릴 수 없음)
3. `prisma migrate deploy`(탈퇴 기록의 이메일, 직접 쓴 사유 칸 삭제)
4. PR 머지 → 운영 배포
- 1~2를 3보다 먼저 해야 한다. 남은 계정을 찾을 때 탈퇴 기록의 이메일을 쓰기 때문.

## 5. 확인한 것(로컬)
- 탈퇴 뒤 게시물, 카테고리, 태그 0개, 탈퇴 기록은 id, reason, createdAt 칸만, 로그인 계정 없음
- 예전 토큰으로 사용자 확인 거절, 예전 쿠키로 접속하면 로그인 화면으로 한 번 이동
- 같은 이메일로 재가입 성공(새 계정 ID)
- 계정 삭제를 일부러 실패시키면 게시물, 카테고리, 탈퇴 기록이 그대로이고 오류 문구가 돌아옴
- 정리 SQL: 탈퇴 뒤 다시 로그인하지 않은 계정만 지우고, 다시 로그인한 계정과 활성 계정은 남김
